# 06 — UX architecture

## The bet

The primary flow is **five taps to a rendered Reel**:

```
Create From Reference → pick video → Use This Style → add photos → Generate
```

Everything else in the app is an *escape hatch* from that line, not a step on it. The editor is
where you go when Auto Arrange was wrong, not where you go to finish the job.

## Screen map

```
Home ──┬── Create From Reference ─▶ Reference Import ─▶ Analysis ─▶ Recipe Summary
       │                                                                  │
       │                                              ┌───────────────────┘
       │                                              ▼
       │                                     Content Import ─▶ Mapping ─▶ Generate
       │                                                                     │
       ├── Start From Scratch ──────────────────────────────▶ Editor ◀───────┘
       │                                                        │
       ├── Recent Projects ─────────────────────────────────────┘
       ├── Recipes (saved styles)                                ▼
       └── Settings                                            Export
```

**Home** deliberately does not have the six-item grid the brief sketched. Research into what
actually gets tapped in mobile editors says one primary action dominates and everything else is
recall. So: one large **Create From Reference** card, a horizontally-scrolling **Continue**
strip of recent projects (thumbnail + relative time, tap to resume exactly where you left), then
a quiet secondary row — *Start From Scratch*, *Saved Styles*. Settings is a toolbar item, not a
tile. Drafts are not a separate destination; an unfinished project *is* a draft and appears in
Continue with a progress ring.

## Analysis screen (§19)

Honest progress, which is harder than a fake percentage and much better:

```
Analysing your video

✓  Read video            15.4s · 1080×1920 · 30fps
✓  Found scenes          12 scenes
✓  Tracked motion        7 camera moves
◐  Reading text          2 layers so far
○  Listening to audio
○  Building style
```

Rules this screen follows:

- **Stages complete, they do not tick up.** Each stage reports a real completion with a real
  result, so the number that appears is information rather than reassurance.
- **Within a stage**, frame-count progress drives an indeterminate-but-moving bar only where the
  denominator is genuinely known (`FrameStream` knows the frame count; OCR does not).
- **Results appear as they land.** By the time the last stage finishes, the user has already read
  most of the summary.
- **Cancel is real** and cooperative — the pipeline checks `Task.isCancelled` every frame.

Then: **"Reference understood"**, with the summary — scene count, duration, aspect, image slots,
text layers, transitions, BPM if found — and a single primary button, **Use This Style**.

Anything below 0.8 confidence carries a small **Guessed** badge. Tapping it shows the `basis`
string in plain language: *"I think this is a push-in because the frame scaled up 17% over six
sampled frames."* This is the feature that makes the app feel honest instead of magic, and it is
free — the data is already in the recipe.

## Mapping screen (§43)

The screen that makes the AI legible. Three columns, one row per scene:

```
      REFERENCE          →     TEMPLATE        →     MY CONTENT
 ┌──────────────┐          wide · 1.2s          ┌──────────────┐
 │ ▓▓▓▓▓▓▓▓▓▓▓▓ │          push-in              │  IMG_2391    │  ⇄
 └──────────────┘          on beat 1            └──────────────┘
```

The reference column **describes the shot rather than showing a frame of it** — "wide · push-in
· 1.2s". That is not a compromise forced by the licensing stance; it is the more accurate
column. What is being reused *is* the structure, and a thumbnail would imply otherwise. It also
means the reference's pixels can be released the moment analysis finishes, which they are.

Tap any assignment → a bottom sheet of your photos ranked for *that* slot, with the reason
("tight crop, high quality"). Swap is one tap. **Auto Arrange** re-solves; **Shuffle** re-solves
with a different diversity seed.

## Editor (§23, §24)

Bottom toolbar, five items — the set that covers the overwhelming majority of real edits:

```
  ✂️ Edit      🔤 Text      🎵 Audio      ✨ Style      📤 Export
```

`Edit` reveals the contextual row for the selected clip (Trim · Split · Speed · Replace ·
Duplicate · Delete). Nothing is nested more than two levels. Progressive disclosure means the
advanced row does not exist until something is selected.

### Timeline

`UIScrollView` in a `UIViewRepresentable` — not SwiftUI. Pinch-zoom over a continuous
seconds-per-point time base needs gesture precision and scroll-offset control that SwiftUI does
not expose, and the consensus for intricate scrubbing widgets remains UIKit.

- Playhead is **fixed at centre**; the timeline moves under it. Scrubbing then costs no
  hand-eye tracking and works one-handed.
- Pinch: 0.5–40 s visible. Snap thresholds scale with zoom, so snapping feels the same at every
  scale.
- Snap targets: clip boundaries, playhead, **beats** (from `beatGrid`). Snap fires a soft
  `.impact(.light)` haptic — the beat grid is felt as much as seen.
- Tracks: video (thumbnail strip), text (chips), audio (waveform). Three lanes maximum on
  screen; more layers scroll vertically inside a fixed height.
- Trim handles are 44 pt targets that overhang the clip edge, so a 0.3 s clip is still grabbable.

### Undo/redo (§25)

Command pattern, not snapshots.

```swift
protocol EditCommand: Sendable {
    var name: String { get }                       // "Trim Clip" — shown in the undo affordance
    func apply(to: inout Timeline) throws
    func revert(to: inout Timeline) throws
}
```

`CommandStack` holds `[EditCommand]` plus a cursor. Continuous gestures (drag, trim) **coalesce**:
the command is created on gesture begin and mutated in place until end, so a 200-frame drag is
one undo step. Undo is a two-finger swipe (a system-level gesture users already know) and a
toolbar button, and it announces what it undid.

Every command is `Codable`, so the stack can be persisted with the project — undo survives a
force-quit. That is unusual, cheap here, and delightful.

## Design system

Native-feeling, not branded-heavy.

- **Type**: SF Pro via `.rounded` design for numerals and controls; Dynamic Type honoured
  throughout, including the timeline's time labels.
- **Colour**: system semantic colours; a single accent (warm rose, matching the sample use case)
  used only for the primary action per screen. Dark mode is the primary design, light mode fully
  supported — video editing happens in the dark.
- **Motion**: `.snappy` for state changes, `.smooth` for content. Nothing over 350 ms. Respects
  `accessibilityReduceMotion` by dropping to cross-fades.
- **Haptics**: selection on snap, light impact on clip grab, success on export complete. Nothing
  else — haptic inflation is worse than silence.
- **Touch targets**: 44 pt minimum, enforced by a `.minimumHitTarget()` modifier rather than by
  vigilance.
- **Bottom sheets** for every secondary choice, with detents. The primary action stays reachable
  by the thumb at all times.
- **Safe areas**: the preview never sits under the home indicator; the timeline's scroll insets
  account for it so a clip can be dragged to the true end.
- **Empty states** propose the next action rather than describing the absence.
- **Accessibility**: every control labelled; timeline exposes scenes as an accessible list with
  `.adjustable` scrubbing; VoiceOver users get the mapping screen as a plain table, which is
  arguably the better version of it.
